# V5 Huashu Actual-Site Contract

Invoke `$huashu-design` with the prepared Source Pack and complete interview. Huashu owns content hierarchy and the entire executable web experience.

## Candidate layout

```text
candidate/
├── index.html
├── styles/
├── scripts/
├── assets/
├── content-bindings.json
├── design-rationale.md
├── manifest.json
└── screenshots/
    ├── desktop.png
    └── mobile.png
```

The candidate uses real content for the hero, priority material, and core interaction. CSS and JavaScript are working local resources. The rationale explains content hierarchy, omitted detail access, responsive behavior, and the main interaction—not a list of stylistic adjectives.

`content-bindings.json` is a traceability index:

```json
{
  "bindings": [
    {
      "contentId": "market-outlook",
      "factIds": ["fact-17"],
      "sourceRefs": ["source-42"],
      "tier": "main",
      "editableKind": "block"
    }
  ]
}
```

It does not contain page, layout, component, chart, or interaction instructions. Each bound element in HTML uses `data-content-id`.

## Final site lineage

After selection, Huashu expands the selected actual site. The final manifest records `parentCandidateSha256`, Source Pack hash, interview hash, and content-bindings hash. The selected design may grow to cover all content, but its experience must not be regenerated by a second design system.

All substantive material is available in `main`, `detail`, or `appendix`. `omitted` requires an explicit user authorization record. All visible values, units, dates, ranges, qualifications, and claims bind to Source Pack facts.

Visible colors use the existing semantic theme variables. Local safe scripts and any safe DOM structure are allowed. Remote runtime dependencies, network calls, dynamic remote imports, `eval`, and `new Function` are forbidden.
